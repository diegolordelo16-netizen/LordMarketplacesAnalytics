# 0. PRINCÍPIOS FUNDAMENTAIS E REGRAS INEGOCIÁVEIS

Este projeto não deverá ser desenvolvido como um simples robô de scraping, extensão de navegador, dashboard ou gerador de anúncios.

O objetivo é construir uma plataforma profissional de inteligência operacional capaz de observar, analisar, diagnosticar, planejar, executar operações autorizadas, acompanhar resultados e melhorar continuamente.

O sistema deverá ser desenvolvido como um produto comercial completo, com arquitetura modular, segurança, autonomia progressiva, memória persistente e capacidade de expansão.

## 0.1. Independência de APIs oficiais dos marketplaces

O sistema deverá funcionar sem depender de:

- API oficial do Mercado Livre.
- API oficial da Shopee.
- API oficial da Amazon.
- API oficial do TikTok Shop.
- API oficial da Shein.
- API oficial da Netshoes.
- Tokens de desenvolvedor dessas plataformas.
- Credenciais de aplicações externas dos marketplaces.
- Contratos comerciais de integração.
- Serviços pagos de terceiros para scraping.
- Plataformas intermediárias de integração de marketplaces.

**A operação principal deverá acontecer através do navegador já autenticado do usuário.**

O usuário deverá abrir normalmente Chrome ou Edge, acessar sua conta e realizar o login manualmente.

A extensão utilizará a sessão de navegação já estabelecida, sem solicitar senhas dos marketplaces dentro do software, cópia manual de cookies, tokens internos ou cadastro de aplicações de desenvolvedor.

Não confundir independência de APIs oficiais com ausência de comunicação HTTP. O navegador naturalmente realiza requisições para carregar páginas e informações.

Poderá ocorrer observação passiva de informações disponibilizadas pela navegação normal, desde que tecnicamente acessíveis.

Não utilizar chamadas diretas a endpoints privados não documentados, não reproduzir requisições autenticadas privadas, não extrair tokens de sessão e não contornar mecanismos de segurança ou controles de acesso.

## 0.2. Operação Local First

O projeto deverá começar funcionando no computador do usuário.

As funcionalidades principais deverão funcionar sem:

- Servidor contratado.
- Banco de dados obrigatório em nuvem.
- Assinatura de plataforma de automação.
- APIs oficiais dos marketplaces.
- Credenciais de desenvolvedor.
- Backend obrigatório de terceiros.
- Infraestrutura externa contratada.
- Configurações técnicas manuais pelo usuário.

A nuvem será uma possibilidade de expansão futura, e não uma exigência para o funcionamento inicial.

## 0.3. Entrega como software comercial

O produto deverá ser entregue como um software Windows completo e instalável.

**Não entregar somente código-fonte, pasta do projeto, extensão separada, arquivos de configuração ou instruções para o usuário montar o ambiente.**

A experiência desejada deverá ser equivalente à instalação de um software comercial:

1. Baixar `MarketplaceIntelligence-Setup.exe`.
2. Executar o arquivo.
3. Clicar em Instalar.
4. Aguardar a instalação automática.
5. Abrir o Marketplace Intelligence.
6. Realizar a configuração inicial do próprio software.
7. Começar a utilizar.

Todos os componentes necessários deverão estar incorporados ao instalador sempre que tecnicamente possível e legalmente permitido.

O usuário não deverá precisar instalar ou configurar manualmente:

- Node.js.
- npm.
- pnpm.
- Python.
- Git.
- SQLite.
- Bibliotecas.
- Frameworks.
- Compiladores.
- Ferramentas de automação.
- Hosts de comunicação.
- Serviços locais.
- Dependências de programação.
- Drivers ou runtimes distribuíveis.

A única dependência ambiental prevista para a automação no navegador será a existência de Chrome ou Edge compatível, ou sua instalação através de canal oficial e mediante autorização do usuário.

Não exigir utilização de terminal, PowerShell, Prompt de Comando ou ferramentas de desenvolvimento.

Se o ambiente de desenvolvimento não permitir gerar diretamente um binário `.exe`, entregar o código completo, os scripts de empacotamento e um workflow reproduzível, preferencialmente GitHub Actions com `windows-latest`, capaz de gerar o instalador sem intervenção técnica manual.

## 0.4. Hierarquia da inteligência

A arquitetura deverá seguir esta hierarquia:

1. A IA interna é o cérebro principal.
2. Os agentes internos executam análises especializadas.
3. A memória operacional acumula conhecimento e resultados.
4. O Gemini atua como consultor, auditor e segunda opinião externa.
5. A Central de Melhorias registra propostas de evolução.
6. Somente a conta proprietária aprova ou rejeita melhorias permanentes no próprio software.

**O Marketplace Intelligence não poderá depender do Gemini para pensar, analisar, aprender ou funcionar.**

Quando a cota gratuita do Gemini acabar, a inteligência interna continuará trabalhando normalmente.

## 0.5. Preservação integral

Nenhuma funcionalidade descrita neste documento poderá ser:

- Excluída.
- Simplificada.
- Substituída por uma demonstração.
- Transformada apenas em elemento visual.
- Deixada como botão sem implementação.
- Desativada silenciosamente.
- Omitida na instalação final.

Se uma funcionalidade não puder ser implementada em determinado marketplace, registrar a limitação específica daquele adapter, preservando sua disponibilidade nas demais plataformas.

## 0.6. Integridade operacional

- Não utilizar dados simulados como se fossem reais.
- Não inventar indicadores ausentes.
- Não afirmar que uma automação foi concluída sem verificar seu resultado.
- Não apresentar estimativas como valores confirmados.
- Registrar origem e data de referência dos dados.
- Diferenciar análises internas de análises revisadas pelo Gemini.
- Registrar todas as decisões relevantes.
- Preservar históricos.
- Não executar ações fora das permissões estabelecidas.

## 4.1. Detecção da sessão

Implementar:

- Detecção de login.
- Detecção de logout.
- Detecção de sessão expirada.
- Identificação de página de login.
- Identificação de redirecionamentos.

- Monitoramento de troca de conta.

## 4.2. Contextos de execução

**ISOLATED WORLD**

Content Scripts responsáveis por leitura do DOM, identificação de elementos, interação com formulários e envio de mensagens.

**MAIN WORLD**

Utilizado somente quando necessário para observação passiva de dados disponibilizados pela página, como respostas acessíveis de fetch e XMLHttpRequest.

Não alterar o comportamento original da página nem realizar replay de requisições privadas.

**SERVICE WORKER**

Responsável por mensagens, coordenação, controle de abas e comunicação com Native Messaging.

Não utilizar memória volátil do Service Worker como armazenamento de estado permanente.

## 4.3. Segurança da comunicação

Dados provenientes do MAIN World serão considerados não confiáveis.

Implementar:

- Validação de schema.
- Validação de origem.
- Tipos.
- Limites de payload.
- Controle de comandos.
- Proteção contra mensagens forjadas.
- Logs de eventos suspeitos.

## 4.4. Captura híbrida

Combinar:

1. DOM.
2. Observação passiva de respostas acessíveis.
3. Navegação assistida.

Não presumir que todos os indicadores estarão disponíveis diretamente.

Se necessário, navegar por telas, relatórios e filtros para obter dados complementares.

## 4.5. Reconhecimento de páginas

# 9. MOTOR DE KPIs E ANÁLISE DE DESEMPENHO

Criar motor matemático centralizado, independente e testável.

## 9.1. Tráfego

- Impressões.
- Cliques.
- Visitas.
- CTR.
- Evolução de tráfego.
- Origem de visitas quando disponível.

`CTR = Cliques / Impressões × 100`

## 9.2. Conversão

- Pedidos.
- Unidades vendidas.
- CVR.
- Adições ao carrinho.
- Favoritos.
- Cancelamentos.
- Devoluções.

`CVR = Pedidos / Visitas × 100`

Diferenciar pedidos, unidades, pedidos pagos, vendas atribuídas e pedidos efetivamente concluídos.

## 9.3. Receita e margem

- GMV.
- Faturamento.
- Receita após descontos.
- Receita líquida.
- Unidades.
- Giro diário.
- Ticket médio.
- Lucro estimado.
- Lucro realizado.
- Margem de contribuição.
- Rentabilidade por anúncio.
- Rentabilidade por SKU.

## 9.4. Ads

- Investimento.
- Vendas atribuídas.
- ROAS.
- ACoS.
- TACoS.
- Custo por venda.
- Participação da publicidade no faturamento.
- Rentabilidade das campanhas.

`ROAS = Receita atribuída a Ads / Investimento em Ads`

`ACoS = Investimento em Ads / Receita atribuída a Ads × 100`

`TACoS = Investimento em Ads / Faturamento total × 100`

## 9.5. Operação

- Estoque.
- Cobertura.
- Média diária de vendas.
- Risco de ruptura.
- Qualidade do cadastro.
- Perguntas pendentes.
- Posição orgânica.
- Alertas.

`Cobertura de estoque = Estoque disponível / Média diária de vendas`

## 9.6. Regras

- Respeitar períodos compatíveis.
- Considerar fuso horário.
- Tratar valores ausentes.
- Evitar divisão por zero.
- Diferenciar receita total e atribuída.
- Evitar contagens duplicadas.
- Utilizar precisão decimal ou centavos inteiros.

As metodologias dos marketplaces deverão ser identificadas. Não presumir que indicadores de plataformas diferentes possuam exatamente a mesma definição.

# 18. ARQUITETURA DE INTELIGÊNCIA: AI DIRECTOR, IA INTERNA E GEMINI

## 18.1. Princípio fundamental

**A IA interna é o cérebro principal do Marketplace Intelligence. O Gemini é um consultor externo e auditor complementar.**

O software deverá funcionar, analisar, aprender e continuar evoluindo sem depender permanentemente do Gemini.

A falta de chave, internet ou cota gratuita não poderá interromper:

- KPIs.
- Motor financeiro.
- Análises determinísticas.
- Memória operacional.
- Ranking.

- Agentes locais.

## 18.2. Camadas da inteligência interna

Responsável por:

- Cálculos.
- KPIs.
- Margens.
- Regras.
- Classificações.
- Limites.
- Detecção de anomalias.
- Validações.

Não depender de IA externa.

### B. AI Director

Agente central que coordena especialistas, combina evidências, prioriza investigações, supervisiona tarefas e avalia resultados.

### C. Agentes internos

Agentes com objetivos e ferramentas específicos.

### D. Memória operacional

Preservar problemas, estratégias, resultados, decisões e lições aprendidas.

### E. Base de conhecimento

Indexar e recuperar o conhecimento operacional acumulado.

### F. Modelo local opcional

Preparar suporte a modelos locais quando houver hardware compatível.

O modelo local poderá ampliar raciocínio e interpretação, mas não será obrigatório para o funcionamento do motor analítico e da memória.

# 39. DEFINIÇÃO FINAL DO PRODUTO

<h2>1. Sumário executivo e objetivo da Entrega 1</h2>

<p class="lead">A Entrega 1 não produz software em execução: produz a arquitetura que impede retrabalho, ambiguidade de responsabilidade e promessas falsas de capacidade.</p>

<p>O Lord Marketplaces Analytics é um software Windows que opera sobre a sessão já autenticada do próprio usuário nos marketplaces, por meio de uma extensão de navegador (Chrome e Edge, Manifest V3), sem depender de APIs oficiais dos marketplaces. O cérebro do produto é uma IA interna: um motor determinístico, um AI Director, nove agentes especializados e uma memória operacional. A Central de Melhorias concentra toda mudança permanente no software e só aceita aprovação da conta OWNER_PRINCIPAL. A entrega final é um instalador único para Windows, com runtime embutido, sem exigir do usuário final Node, Python, Git, npm ou terminal.</p>

<h3>3.1 Camada de Extensão (navegador)</h3>
<p>Chrome e Edge, Manifest V3, construída em React + TypeScript + Vite + Tailwind, com Dexie (IndexedDB) como cache local de curta duração. É a única camada que toca a página do marketplace.</p>
<ul>
  <li><b>Side Panel</b> — interface principal do usuário ao lado do marketplace: status de conexão com o serviço local, conta detectada, página reconhecida, dados coletados, missões do dia.</li>
  <li><b>Content scripts</b> — leitura estruturada do DOM da página reconhecida; nunca escrevem no marketplace sem comando explícito e autorizado.</li>
  <li><b>Service worker</b> — orquestração entre content scripts, MAIN world observer, Dexie e o canal com o serviço local; sem estado de negócio (o estado de negócio vive no SQLite).</li>
  <li><b>MAIN world observer (passivo)</b> — script injetado no contexto da página para observar o que ela já carregou. Não reproduz requisições, não chama endpoints privados, não injeta sessão.</li>
</ul>

<h3>3.2 Camada de Serviço Local persistente</h3>
<p>Processo Node + TypeScript residente na máquina do usuário. É o cérebro operacional: não depende do navegador estar aberto para processar filas, calcular indicadores ou executar missões já agendadas.</p>
<ul>
  <li><b>SQLite + Drizzle + Zod</b> — persistência, schema tipado e validação de fronteira.</li>
  <li><b>Filas e scheduler</b> — capturas, cálculos, ciclos de agente, ciclos Gemini, backups; retentativas idempotentes.</li>
  <li><b>Motores</b> — KPIs, financeiro em centavos, simulador de margem, Score de Prioridade e Saúde, Missões do Dia (Seção 9).</li>
  <li><b>IA interna</b> — motor determinístico, AI Director, 9 agentes, memória operacional, AI Tool Registry (Seção 10).</li>
  <li><b>Integração Gemini</b> — consultor externo, gerenciador de cotas, cache, Workspace de Debate (Seção 11).</li>
  <li><b>Central de Melhorias</b> — propostas, aprovação exclusiva, auto-upgrade governado (Seção 12).</li>
</ul>

<h3>3.3 Native Messaging Host</h3>
<p>Executável local registrado por usuário no Windows, que fala com a extensão pelo protocolo nativo do navegador (stdin/stdout com mensagens prefixadas por tamanho). É o caminho de transporte de produção, disponível somente após a extensão ter ID fixo (Seção 4).</p>

<h3>3.4 Banco local SQLite</h3>
<p>Arquivo único no perfil do usuário, modo WAL para leitura concorrente durante escrita, migrations versionadas e aplicadas de forma transacional na inicialização, backups automáticos antes de migrations e antes de auto-upgrades.</p>

<h3>3.5 Backend em nuvem opcional</h3>
<p>Postgres/Supabase, opcional, nunca obrigatório. Serve apenas para sincronização entre máquinas do mesmo proprietário e para backups externos autorizados. Nenhum fluxo da POC ou da operação diária pode depender dele.</p>

<h3>3.6 Camada de distribuição Windows</h3>
<p>Instalador único, updater com verificação de assinatura, desinstalador com dois níveis, registro do Native Messaging Host por usuário, verificação de integridade e checksums (Seção 13).</p>

<h2>4. A decisão crítica da Entrega 1: como a extensão fala com o serviço local</h2>

<p class="lead">Todo o produto depende de um único tubo: a extensão precisa conversar com o serviço local, de forma segura, sem depender de APIs dos marketplaces e sem exigir publicação prévia nas lojas.</p>

<h3>4.1 A restrição real</h3>
<p>O Chrome Native Messaging exige que a extensão tenha identidade estável: o manifesto do Native Messaging Host lista os IDs de extensão autorizados, e o navegador só entrega a porta nativa a uma extensão instalada cujo ID corresponda. Em extensão carregada sem empacotamento (modo desenvolvedor), o ID depende da chave de empacotamento e o fluxo não é o mesmo de uma extensão instalada pela loja ou por política corporativa. Consequência direta: <b>Native Messaging não pode ser a ponte da prova de conceito</b> — ele só é confiável depois que a extensão estiver publicada (Chrome Web Store / Edge Add-ons) ou distribuída por política corporativa, com ID fixo e definitivo.</p>

<h3>Chaves, índices e constraints</h3>
<ul>
  <li>Chaves primárias: UUID v4 gerado no serviço local, com coluna <code>created_at</code> em UTC.</li>
  <li>Chaves naturais por marketplace: <code>(marketplace_id, account_id, external_id)</code> único por entidade — impede duplicação em recaptura.</li>
  <li>Séries temporais: índice composto <code>(entity_id, reference_date, collected_at)</code>; nunca sobrescrever histórico, sempre inserir nova observação.</li>
  <li>Dinheiro: armazenado em centavos, inteiro, com coluna de moeda explícita; nunca ponto flutuante.</li>
  <li>Constraints de domínio: status em enumeração fechada; FK com <code>ON DELETE RESTRICT</code> em dados auditáveis; <code>CHECK</code> para valores não negativos onde aplicável.</li>
  <li>Migrações Drizzle versionadas e transacionais; migration aplicada é imutável.</li>
</ul>

<h3>Proveniência obrigatória</h3>
<p>Nenhum dado entra no banco sem registro de proveniência completo. Dado sem proveniência é rejeitado na escrita, não aceito com campo nulo.</p>
<table class="data">
  <thead><tr><th>Campo de proveniência</th><th>Conteúdo</th></tr></thead>
  <tbody>
    <tr><td>fonte</td><td>Página, endpoint público renderizado ou entrada manual</td></tr>
    <tr><td>marketplace</td><td>ML, Shopee, etc.</td></tr>
    <tr><td>conta</td><td>Conta/loja identificada</td></tr>
    <tr><td>página</td><td>Tipo de página reconhecida e URL (sem parâmetros sensíveis)</td></tr>
    <tr><td>data de referência</td><td>Período a que o dado se refere no marketplace</td></tr>
    <tr><td>data de coleta</td><td>Momento da observação</td></tr>
    <tr><td>método</td><td>Adapter + versão + estratégia de leitura</td></tr>
    <tr><td>status de qualidade</td><td>Um dos sete status abaixo</td></tr>
  </tbody>
</table>
<p><b>Status de qualidade:</b> <code>ZERO</code> (valor real igual a zero), <code>UNKNOWN</code> (desconhecido), <code>NOT_COLLECTED</code> (não coletado), <code>UNAVAILABLE</code> (indisponível na página), <code>ESTIMATED</code> (estimado, com método registrado), <code>CALCULATED</code> (derivado de outros dados), <code>VERIFIED</code> (confirmado por segunda leitura ou verificação pós-ação). A interface sempre mostra o status; <code>ESTIMATED</code> nunca aparece como se fosse <code>VERIFIED</code>.</p>

<h2>9. Motores analíticos</h2>

<h3>Motor de KPIs</h3>
<table class="data">
  <thead><tr><th>Indicador</th><th>Fórmula</th><th>Observação</th></tr></thead>
  <tbody>
    <tr><td>CTR</td><td>cliques ÷ impressões × 100</td><td>Indisponível se impressões ausentes → <code>UNAVAILABLE</code></td></tr>
    <tr><td>CVR</td><td>conversões ÷ cliques × 100</td><td>Base de cliques deve ser do mesmo período</td></tr>
    <tr><td>ROAS</td><td>receita atribuída ÷ investimento em ads</td><td>Sem atribuição, resultado marcado <code>ESTIMATED</code></td></tr>
    <tr><td>ACoS</td><td>investimento em ads ÷ receita atribuída × 100</td><td>Inverso do ROAS</td></tr>
    <tr><td>TACoS</td><td>investimento em ads ÷ receita total × 100</td><td>Receita total inclui vendas orgânicas</td></tr>
    <tr><td>Ticket médio</td><td>receita total ÷ número de pedidos</td><td>Zero pedidos → <code>ZERO</code>, não divisão por zero</td></tr>
    <tr><td>Cobertura de estoque</td><td>unidades em estoque ÷ consumo médio diário</td><td>Resultado em dias; consumo sem histórico suficiente → <code>ESTIMATED</code></td></tr>
  </tbody>
</table>

<h3>Motor financeiro, simulador e priorização</h3>
<ul>
  <li>Todos os valores em <b>centavos inteiros</b>; arredondamento explícito e único na borda de apresentação.</li>
  <li><b>Versionamento histórico</b> de custos e de taxas: cada alteração cria nova versão com vigência; o cálculo de um período usa a versão vigente naquele período, nunca a atual.</li>
  <li><b>Simulador de margem</b>: receita menos taxas do marketplace, custo do produto, frete, impostos informados e ads, por cenário, com a memória de cálculo visível.</li>
  <li>Toda saída do motor é <code>CALCULATED</code>, com a versão das tabelas de custo e taxa usadas registrada junto.</li>
  <li><b>Score de Prioridade e Saúde</b>: o motor determinístico combina indicadores, cobertura de estoque, margem e tendência, com pesos versionados e critérios explícitos.</li>
  <li><b>Missões do Dia</b>: a partir do score, uma lista curta de ações priorizadas, cada uma com motivo, dado de origem e resultado esperado. A lista é reproduzível: os mesmos dados e a mesma versão de pesos produzem a mesma lista.</li>
</ul>

<h2>10. Camada de inteligência</h2>

<p class="lead">Hierarquia fixa: motor determinístico → AI Director → 9 agentes → memória operacional → Gemini como auditor. Nenhuma seta sobe.</p>

<div class="timeline">
  <div><div class="when">Base</div><b>Motor determinístico</b> — cálculos, scores, regras e prioridades reproduzíveis.</div>
  <div><div class="when">Coordenação</div><b>AI Director</b> — distribui trabalho, arbitra conflitos entre agentes, consolida recomendações.</div>
  <div><div class="when">Execução</div><b>9 agentes</b> — SEO, Ads, Concorrência, Conversão, Financeiro, Estoque, Conteúdo, Precificação, Performance.</div>
  <div><div class="when">Persistência</div><b>Memória operacional</b> — o que foi tentado, previsão e resultado, para calibrar decisões futuras.</div>
  <div><div class="when">Externo</div><b>Gemini</b> — consultor e auditor em ciclos limitados; não decide, não executa.</div>
</div>

<h3>Contrato de agente</h3>
<table class="data">
  <thead><tr><th>Campo</th><th>Conteúdo</th></tr></thead>
  <tbody>
    <tr><td>Objetivo</td><td>Uma frase mensurável e restrita ao domínio do agente</td></tr>
    <tr><td>Ferramentas</td><td>Lista fechada de ferramentas do AI Tool Registry que o agente pode chamar</td></tr>
    <tr><td>Entradas</td><td>Consultas permitidas, com proveniência obrigatória; sem acesso a segredos</td></tr>
    <tr><td>Saídas</td><td>Recomendações tipadas, com justificativa, dados de origem e nível de confiança</td></tr>

<h3>AI Tool Registry, feedback loop e operação offline</h3>
<ul>
  <li><b>AI Tool Registry</b> — nenhum agente executa ferramenta não cadastrada. O registro define nome, versão, entrada, saída, permissões, efeito colateral (leitura, escrita local, ação no marketplace) e se exige aprovação humana. Chamada a ferramenta inexistente é erro de contrato, não exceção silenciosa.</li>
  <li><b>Feedback loop</b> — cada recomendação relevante gera uma previsão registrada (<code>predictions</code>). Após a janela de observação, o resultado real é capturado e gravado (<code>prediction_outcomes</code>). A memória operacional usa essa comparação para ajustar confiança dos agentes e pesos de priorização — nunca para reescrever o histórico.</li>
  <li><b>Sem Gemini e sem internet</b> — motor determinístico, AI Director, agentes, memória, missões e relatórios operam integralmente offline. Sem Gemini, o sistema perde apenas a consultoria externa e a auditoria de terceiro; a interface declara isso explicitamente e não simula a resposta ausente.</li>
</ul>

<h2>19. Glossário e próximos passos</h2>

<div class="cols-2">
  <div>
    <h3>Glossário</h3>
    <ul>
      <li><b>Local First</b> — dados e decisão na máquina do usuário; nuvem opcional.</li>
      <li><b>MV3</b> — Manifest V3, modelo de extensão do Chrome e Edge.</li>
      <li><b>Side Panel</b> — painel lateral da extensão junto à página.</li>
      <li><b>MAIN world</b> — contexto JavaScript da própria página, tratado como não confiável.</li>
