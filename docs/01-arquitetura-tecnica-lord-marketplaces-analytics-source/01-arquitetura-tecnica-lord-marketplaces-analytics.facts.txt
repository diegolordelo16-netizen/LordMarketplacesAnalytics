# 0. PRINCÍPIOS FUNDAMENTAIS E REGRAS INEGOCIÁVEIS

Este projeto não deverá ser desenvolvido como um simples robô de scraping, extensão de navegador, dashboard ou gerador de anúncios.

O objetivo é construir uma plataforma profissional de inteligência operacional capaz de observar, analisar, diagnosticar, planejar, executar operações autorizadas, acompanhar resultados e melhorar continuamente.

O sistema deverá ser desenvolvido como um produto comercial completo, com arquitetura modular, segurança, autonomia progressiva, memória persistente e capacidade de expansão.

## 0.1. Independência de APIs oficiais dos marketplaces

O sistema deverá funcionar sem depender de:

- API oficial do Mercado Livre.
- API oficial da Shopee.
- API oficial da Amazon.
- API oficial do TikTok Shop.
- API oficial da Shein.
- API oficial da Netshoes.
- Tokens de desenvolvedor dessas plataformas.
- Credenciais de aplicações externas dos marketplaces.
- Contratos comerciais de integração.
- Serviços pagos de terceiros para scraping.
- Plataformas intermediárias de integração de marketplaces.

**A operação principal deverá acontecer através do navegador já autenticado do usuário.**

O usuário deverá abrir normalmente Chrome ou Edge, acessar sua conta e realizar o login manualmente.

A extensão utilizará a sessão de navegação já estabelecida, sem solicitar senhas dos marketplaces dentro do software, cópia manual de cookies, tokens internos ou cadastro de aplicações de desenvolvedor.

Não confundir independência de APIs oficiais com ausência de comunicação HTTP. O navegador naturalmente realiza requisições para carregar páginas e informações.

Poderá ocorrer observação passiva de informações disponibilizadas pela navegação normal, desde que tecnicamente acessíveis.

Não utilizar chamadas diretas a endpoints privados não documentados, não reproduzir requisições autenticadas privadas, não extrair tokens de sessão e não contornar mecanismos de segurança ou controles de acesso.

## 0.2. Operação Local First

O projeto deverá começar funcionando no computador do usuário.

As funcionalidades principais deverão funcionar sem:

- Servidor contratado.
- Banco de dados obrigatório em nuvem.
- Assinatura de plataforma de automação.
- APIs oficiais dos marketplaces.
- Credenciais de desenvolvedor.
- Backend obrigatório de terceiros.
- Infraestrutura externa contratada.
- Configurações técnicas manuais pelo usuário.

A nuvem será uma possibilidade de expansão futura, e não uma exigência para o funcionamento inicial.

## 0.3. Entrega como software comercial

O produto deverá ser entregue como um software Windows completo e instalável.

**Não entregar somente código-fonte, pasta do projeto, extensão separada, arquivos de configuração ou instruções para o usuário montar o ambiente.**

A experiência desejada deverá ser equivalente à instalação de um software comercial:

1. Baixar `MarketplaceIntelligence-Setup.exe`.
2. Executar o arquivo.
3. Clicar em Instalar.
4. Aguardar a instalação automática.
5. Abrir o Marketplace Intelligence.
6. Realizar a configuração inicial do próprio software.
7. Começar a utilizar.

Todos os componentes necessários deverão estar incorporados ao instalador sempre que tecnicamente possível e legalmente permitido.

O usuário não deverá precisar instalar ou configurar manualmente:

- Node.js.
- npm.
- pnpm.
- Python.
- Git.
- SQLite.
- Bibliotecas.
- Frameworks.
- Compiladores.
- Ferramentas de automação.
- Hosts de comunicação.
- Serviços locais.
- Dependências de programação.
- Drivers ou runtimes distribuíveis.

A única dependência ambiental prevista para a automação no navegador será a existência de Chrome ou Edge compatível, ou sua instalação através de canal oficial e mediante autorização do usuário.

Não exigir utilização de terminal, PowerShell, Prompt de Comando ou ferramentas de desenvolvimento.

Se o ambiente de desenvolvimento não permitir gerar diretamente um binário `.exe`, entregar o código completo, os scripts de empacotamento e um workflow reproduzível, preferencialmente GitHub Actions com `windows-latest`, capaz de gerar o instalador sem intervenção técnica manual.

## 0.4. Hierarquia da inteligência

A arquitetura deverá seguir esta hierarquia:

1. A IA interna é o cérebro principal.
2. Os agentes internos executam análises especializadas.
3. A memória operacional acumula conhecimento e resultados.
4. O Gemini atua como consultor, auditor e segunda opinião externa.
5. A Central de Melhorias registra propostas de evolução.
6. Somente a conta proprietária aprova ou rejeita melhorias permanentes no próprio software.

**O Marketplace Intelligence não poderá depender do Gemini para pensar, analisar, aprender ou funcionar.**

Quando a cota gratuita do Gemini acabar, a inteligência interna continuará trabalhando normalmente.

## 0.5. Preservação integral

Nenhuma funcionalidade descrita neste documento poderá ser:

- Excluída.
- Simplificada.
- Substituída por uma demonstração.
- Transformada apenas em elemento visual.
- Deixada como botão sem implementação.
- Desativada silenciosamente.
- Omitida na instalação final.

Se uma funcionalidade não puder ser implementada em determinado marketplace, registrar a limitação específica daquele adapter, preservando sua disponibilidade nas demais plataformas.

## 0.6. Integridade operacional

- Não utilizar dados simulados como se fossem reais.
- Não inventar indicadores ausentes.
- Não afirmar que uma automação foi concluída sem verificar seu resultado.
- Não apresentar estimativas como valores confirmados.
- Registrar origem e data de referência dos dados.
- Diferenciar análises internas de análises revisadas pelo Gemini.
- Registrar todas as decisões relevantes.
- Preservar históricos.
- Não executar ações fora das permissões estabelecidas.

## 4.1. Detecção da sessão

Implementar:

- Detecção de login.
- Detecção de logout.
- Detecção de sessão expirada.
- Identificação de página de login.
- Identificação de redirecionamentos.

- Monitoramento de troca de conta.

## 4.2. Contextos de execução

**ISOLATED WORLD**

Content Scripts responsáveis por leitura do DOM, identificação de elementos, interação com formulários e envio de mensagens.

**MAIN WORLD**

Utilizado somente quando necessário para observação passiva de dados disponibilizados pela página, como respostas acessíveis de fetch e XMLHttpRequest.

Não alterar o comportamento original da página nem realizar replay de requisições privadas.

**SERVICE WORKER**

Responsável por mensagens, coordenação, controle de abas e comunicação com Native Messaging.

Não utilizar memória volátil do Service Worker como armazenamento de estado permanente.

## 4.3. Segurança da comunicação

Dados provenientes do MAIN World serão considerados não confiáveis.

Implementar:

- Validação de schema.
- Validação de origem.
- Tipos.
- Limites de payload.
- Controle de comandos.
- Proteção contra mensagens forjadas.
- Logs de eventos suspeitos.

## 4.4. Captura híbrida

Combinar:

1. DOM.
2. Observação passiva de respostas acessíveis.
3. Navegação assistida.

Não presumir que todos os indicadores estarão disponíveis diretamente.

Se necessário, navegar por telas, relatórios e filtros para obter dados complementares.

## 4.5. Reconhecimento de páginas

# 9. MOTOR DE KPIs E ANÁLISE DE DESEMPENHO

Criar motor matemático centralizado, independente e testável.

## 9.1. Tráfego

- Impressões.
- Cliques.
- Visitas.
- CTR.
- Evolução de tráfego.
- Origem de visitas quando disponível.

`CTR = Cliques / Impressões × 100`

## 9.2. Conversão

- Pedidos.
- Unidades vendidas.
- CVR.
- Adições ao carrinho.
- Favoritos.
- Cancelamentos.
- Devoluções.

`CVR = Pedidos / Visitas × 100`

Diferenciar pedidos, unidades, pedidos pagos, vendas atribuídas e pedidos efetivamente concluídos.

## 9.3. Receita e margem

- GMV.
- Faturamento.
- Receita após descontos.
- Receita líquida.
- Unidades.
- Giro diário.
- Ticket médio.
- Lucro estimado.
- Lucro realizado.
- Margem de contribuição.
- Rentabilidade por anúncio.
- Rentabilidade por SKU.

## 9.4. Ads

- Investimento.
- Vendas atribuídas.
- ROAS.
- ACoS.
- TACoS.
- Custo por venda.
- Participação da publicidade no faturamento.
- Rentabilidade das campanhas.

`ROAS = Receita atribuída a Ads / Investimento em Ads`

`ACoS = Investimento em Ads / Receita atribuída a Ads × 100`

`TACoS = Investimento em Ads / Faturamento total × 100`

## 9.5. Operação

- Estoque.
- Cobertura.
- Média diária de vendas.
- Risco de ruptura.
- Qualidade do cadastro.
- Perguntas pendentes.
- Posição orgânica.
- Alertas.

`Cobertura de estoque = Estoque disponível / Média diária de vendas`

## 9.6. Regras

- Respeitar períodos compatíveis.
- Considerar fuso horário.
- Tratar valores ausentes.
- Evitar divisão por zero.
- Diferenciar receita total e atribuída.
- Evitar contagens duplicadas.
- Utilizar precisão decimal ou centavos inteiros.

As metodologias dos marketplaces deverão ser identificadas. Não presumir que indicadores de plataformas diferentes possuam exatamente a mesma definição.

# 18. ARQUITETURA DE INTELIGÊNCIA: AI DIRECTOR, IA INTERNA E GEMINI

## 18.1. Princípio fundamental

**A IA interna é o cérebro principal do Marketplace Intelligence. O Gemini é um consultor externo e auditor complementar.**

O software deverá funcionar, analisar, aprender e continuar evoluindo sem depender permanentemente do Gemini.

A falta de chave, internet ou cota gratuita não poderá interromper:

- KPIs.
- Motor financeiro.
- Análises determinísticas.
- Memória operacional.
- Ranking.

- Agentes locais.

## 18.2. Camadas da inteligência interna

Responsável por:

- Cálculos.
- KPIs.
- Margens.
- Regras.
- Classificações.
- Limites.
- Detecção de anomalias.
- Validações.

Não depender de IA externa.

### B. AI Director

Agente central que coordena especialistas, combina evidências, prioriza investigações, supervisiona tarefas e avalia resultados.

### C. Agentes internos

Agentes com objetivos e ferramentas específicos.

### D. Memória operacional

Preservar problemas, estratégias, resultados, decisões e lições aprendidas.

### E. Base de conhecimento

Indexar e recuperar o conhecimento operacional acumulado.

### F. Modelo local opcional

Preparar suporte a modelos locais quando houver hardware compatível.

O modelo local poderá ampliar raciocínio e interpretação, mas não será obrigatório para o funcionamento do motor analítico e da memória.

# 39. DEFINIÇÃO FINAL DO PRODUTO

O software deverá aprender continuamente com suas operações, sem exigir que o Gemini esteja disponível o tempo inteiro.

O produto deverá iniciar no computador do usuário e possuir possibilidade de expansão para SaaS.
